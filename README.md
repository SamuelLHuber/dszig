# DSZig

[DSPy](https://github.com/stanfordnlp/dspy) in Zig: declarative LM programs
whose signatures are checked at compile time. DSZig follows DSPy 3.4.1. It
sends the same prompts, parses completions the same way, picks the same
BootstrapFewShot demos and saves the same `program.save()` JSON. Golden tests
generated by real DSPy check all four.

- Zig 0.17.0, no dependencies (`build.zig.zon` `.dependencies = .{}`)
- Every allocation comes from an allocator you pass in. Trace, LM and
  retriever are carried in an explicit `Context`, with no global settings.
- Tested against allocation failure at every point (`checkAllAllocationFailures`)
  and with fixed-buffer allocators

```zig
const dszig = @import("dszig");

const QA = dszig.Signature(struct {
    pub const instructions = "Answer questions with short factoid answers.";
    pub const Input = struct { context: []const []const u8, question: []const u8 };
    pub const Output = struct { answer: []const u8 };
    pub const descriptions = .{ .answer = "often between 1 and 5 words" };
});

const RAG = struct {
    retrieve: dszig.Retrieve = .{ .k = 2 },
    generate_answer: dszig.ChainOfThought(QA) = .{},
    compiled: bool = false,

    pub const Input = struct { question: []const u8 };
    pub const Output = dszig.ChainOfThought(QA).Output; // { reasoning, answer }

    pub fn forward(self: *const RAG, ctx: dszig.Context, input: Input) dszig.predict.Error!Output {
        const context = try self.retrieve.forward(ctx, input.question);
        return self.generate_answer.forward(ctx, .{ .context = context, .question = input.question });
    }
};

// var client: dszig.lm.OpenAI = .{ .client = &http, .base_url = "https://api.openai.com/v1", .model = "gpt-4o-mini", .api_key = key };
const ctx: dszig.Context = .{ .arena = arena, .lm = client.lm(), .retriever = corpus.retriever() };
const out = try (RAG{}).forward(ctx, .{ .question = "What is the capital of France?" });

const optimizer: dszig.BootstrapFewShot = .{ .metric = metric, .max_bootstrapped_demos = 2 };
const result = try optimizer.compile(RAG, arena, gpa, ctx, .{}, null, trainset);
try dszig.state.save(arena, &result.program, writer); // loads in DSPy: program.load(path)
```

Runnable versions: [`examples/rag.zig`](examples/rag.zig) (`zig build rag`)
and [`examples/bootstrap.zig`](examples/bootstrap.zig)
(`zig build bootstrap -- rag.json`).

## What is implemented

| DSPy 3.4.1 | DSZig |
|---|---|
| `dspy.Signature` (class-based) | `dszig.Signature(Spec)`, built at comptime from `Input`/`Output` structs with optional `instructions` and `descriptions`. Field types are `str` (`[]const u8`), `list[str]` (`[]const []const u8`), `bool`, `int` (any integer), `float` (`f32`/`f64`) and `Literal[...]` (exhaustive enum). Prefixes and default instructions are inferred as DSPy does. |
| `ChatAdapter`, `JSONAdapter` | `dszig.Adapter.chat` / `.json`. They produce the same system/demo/user messages, field-structure notes and `[[ ## field ## ]]` markers, and parse the same way: first section wins, every output is required, unknown JSON keys are dropped, the JSON object is extracted from surrounding text. A failed chat parse falls back to JSON, as in DSPy. |
| `dspy.LM` | The `dszig.LM` vtable. Provided implementations are `lm.OpenAI` (OpenAI-compatible `/chat/completions` over `std.http`), `lm.ScriptedLM`, `lm.KeywordLM` and `lm.History`. |
| `Predict`, `ChainOfThought`, `Retrieve` | Same names. `ChainOfThought` prepends `reasoning` to the signature at comptime. `predict.InMemoryRetriever` ranks passages by lexical overlap. |
| `named_parameters()` / `named_predictors()` | `predict.namedParameters` / `namedPredictors` walk the struct at comptime and produce DSPy's names (`self`, `generate_answer.predict`, `hops[0]`). Compiled sub-modules are skipped. |
| Trace (`dspy.settings.trace`) | `dszig.Trace`, passed explicitly through `Context.trace`. Each step records the predictor, a deep copy of its inputs and its outputs. |
| `Evaluate` | `optimize.evaluate`: `round(100 * sum / n, 2)`, with a `max_errors` limit |
| `LabeledFewShot`, `BootstrapFewShot` | Same semantics: `max_bootstrapped_demos`, `max_labeled_demos`, `max_rounds` (with `rollout_id`/`temperature=1.0` on later rounds), `metric_threshold`, the example excluded from its own teacher demos, and `compiled` freezing. Sampling and shuffling use `pyrandom`, a port of CPython's MT19937 `random.Random(0)`, so the chosen demos match DSPy's. |
| `module.save(path)` / `load` (JSON) | `state.save` / `saveAlloc` / `load`, which read and write the same file format byte for byte (`json.dumps(indent=2)` style, Python float formatting). |

## Proof of compatibility

`zig build test` runs:

- **Golden tests** ([`tests/golden.zig`](tests/golden.zig)) against fixtures
  produced by DSPy 3.4.1 ([`tools/dspy_reference`](tools/dspy_reference)).
  The `ChainOfThought`, typed-field and multi-line-instruction prompts must
  match byte for byte for both adapters, with demos that are complete,
  partial and augmented. Parsed outputs must be equal. The BootstrapFewShot
  RAG artifact DSZig compiles must match the one DSPy saves, and
  load→save must round-trip it.
- **Behaviour tests** ([`tests/behavior.zig`](tests/behavior.zig)):
  - Evaluate scores match DSPy's.
  - BootstrapFewShot over three generations never lowers the score
    (40 → 80 → 100 → 100) with an LM that improves when given demos.
  - Identical forward passes produce identical traces.
  - `compile` is deterministic and does not mutate the student. It refuses
    compiled students.
  - Compiled sub-modules are frozen.
  - Compiling, evaluating and saving inside fixed buffers leaves the scratch
    allocator empty after every example.
  - `checkAllAllocationFailures` passes over compile+save.
- **Compile-fail tests** ([`tests/compile_fail`](tests/compile_fail)). Each
  signature below must be rejected with its specific `@compileError`: no
  outputs, a field that is both input and output, a non-`\w+` name, the
  reserved name `completed`, a description for an unknown field, an
  unsupported type, a non-exhaustive enum, or a missing `Output`.

`tools/dspy_reference/check.sh` (part of `devenv test` and CI) runs against
real DSPy:

1. DSPy 3.4.1 regenerates `tests/fixtures` with no changes.
2. DSPy `load()`s the artifact written by `zig build bootstrap` and its
   `save()` produces the same bytes.
3. DSPy replays both committed real-model transcripts in
   [`tests/fixtures/live`](tests/fixtures/live) and reproduces every
   request, output, Evaluate score and compiled artifact.

### Real-model traces (gpt-4o-mini)

Each transcript holds every request a runtime sent to the real OpenAI model,
with the completion it got back: 45 calls in all. It covers the five
adapter cases and two Evaluate → BootstrapFewShot → Evaluate pipelines:

| Pipeline | Data | Baseline | Optimized |
|---|---|---|---|
| RAG (`Retrieve` + `ChainOfThought`) | 5 questions | 100.0% | 100.0% |
| Dates (`ChainOfThought`, exact match) | 12 train / 12 held-out dev | 0.0% | 100.0% |

The dates task ([`examples/dates.json`](examples/dates.json)) uses gold
answers in ISO 8601 form (`1969-07-20`), and the instructions never say so.
Zero-shot, gpt-4o-mini writes dates like "July 20, 1969" and gets every
question wrong. After BootstrapFewShot (4 bootstrapped and 8 labeled demos)
it answers all 12 held-out questions correctly. DSPy and DSZig each
recorded these scores in their own live runs.

There are two transcripts, one per direction:

- `dspy_gpt-4o-mini.json` was recorded by DSPy 3.4.1
  (`tools/dspy_reference/live.py`). [`tests/live_replay.zig`](tests/live_replay.zig)
  replays it through DSZig with `lm.ReplayLM`. Every DSZig request must
  byte-match a recorded DSPy request, and every recorded call must be used.
  The parsed outputs, both scores and the compiled artifact must then equal
  DSPy's.
- `dszig_gpt-4o-mini.json` was recorded by DSZig's own `std.http` OpenAI
  client (`zig build live`, `lm.RecordingLM`). `check_live.py` replays it
  through DSPy and applies the same checks in reverse.

Replays need no key, so CI runs them. To re-record, run `dz-live` with
`OPENAI_API_KEY` set. Real completions vary from run to run, so a
re-recorded transcript differs, but the replay checks must still pass.

## Not implemented (v0.1)

- MIPROv2, COPRO, GEPA, BootstrapFewShotWithRandomSearch, Ensemble
- ReAct / tool calling, streaming, async/parallel execution, LM caching
- Nested structs, Pydantic models, `dict`, `Optional`, images and other
  custom types as fields
- Saving LM state (`"lm": null` is written, and loading ignores it)

## Known divergences from DSPy 3.4.1

- If one predictor runs several times while bootstrapping a single example
  (multi-hop loops), DSPy keeps one of those traces at random, seeded by a
  cloudpickle hash of the demos. DSZig keeps the most recent trace. Programs
  that call each predictor once per example, which covers every program
  tested here, give identical results.
- DSPy 3.4.1 cannot `save()` a program that contains a `dspy.Retrieve`:
  `Retrieve.dump_state()` does not accept the `json_mode` argument that
  `BaseModule.dump_state` passes it. The reference harness subclasses
  `Retrieve` to accept that argument. DSZig writes the state DSPy would have
  written.
- The OpenAI client sends `response_format: json_object` for JSONAdapter.
  DSPy sends a structured-outputs JSON schema. The prompt messages are the
  same; only this request option differs. CI makes no network calls; the
  live path is exercised by `dz-live`.

## Development

```sh
devenv shell     # Zig 0.17.0, CPython 3.11, uv
dz-test          # zig build test
dz-examples      # zig build examples
dz-dspy          # cross-check against DSPy 3.4.1
dz-check         # all of the above, Debug and ReleaseSafe (what devenv test runs)
dz-live          # re-record real-model transcripts (needs OPENAI_API_KEY)
devenv test
```

Without Nix: install Zig 0.17.0 and run `zig build test examples`.
